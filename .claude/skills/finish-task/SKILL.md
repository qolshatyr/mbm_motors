# Завершение задачи в MBM Motors

В проекте сложился устойчивый ритуал: каждую задачу закрывают проверенным
коммитом, обновлённым `PROJECT_CONTEXT.md` и PR. Новый чат продолжает
работу именно по `PROJECT_CONTEXT.md`, поэтому пропущенное обновление
контекста потом обходится дороже, чем сама задача.

Перед началом прочитай
`~/.agents/skills/verification-before-completion/SKILL.md`, если он есть:
он запрещает заявлять об успехе без свежих доказательств.

## 1. Проверки по типу изменений

Запускай то, что затрагивает изменение, а не всё подряд:

| Что менялось | Проверка |
| --- | --- |
| Java, ресурсы, миграции, `pom.xml` | `./mvnw verify` (Spotless, тесты, JaCoCo). Если формат не прошёл, `./mvnw spotless:apply` и повтор |
| Python в `tools/`, `scripts/` | `python3 -m unittest discover -s tests -v` |
| `frontend/` | `(cd frontend && npm ci && npm run build)` |
| Поведение в браузере | Нужный сценарий из `tests/browser/` на запущенном сайте (`webapp-testing`) |
| JSON в `postman/assets/` | `python3 -m json.tool <файл> > /dev/null` |
| Только документы | Проверь ссылки и пути; сборку можно не запускать, но так и напиши |

Тесты с PostgreSQL требуют Docker или базу `mbm_test`. Пропущенные тесты
и недоступные проверки называй прямо: в ответе, в `PROJECT_CONTEXT.md` и в
описании PR.

## 2. Обновление `PROJECT_CONTEXT.md`

Это постоянное правило пользователя (раздел 1 файла).

- В разделе «2. Текущий этап» замени верхний абзац новым: дата, что
  запросил пользователь, что сделано, что проверено и что нет,
  ограничения, следующий шаг.
- Прежнюю запись «Предыдущий этап» перенеси дословно в начало раздела 1
  `docs/Project_History.md`, а прежнюю текущую запись сделай «Предыдущим
  этапом». В `PROJECT_CONTEXT.md` остаются сводка и две последние записи.
- Если задача меняет факты сводки (что реализовано, ветки, CI, запреты),
  поправь сводку.
- Не записывай секреты, токены и данные покупателей.
- Отделяй проверенные факты от предложений и открытых вопросов.
- Если задача сделала устаревшим какой-то раздел, поправь его или явно
  пометь как историю.

## 3. Ветка и коммит

- Работай в ветке задачи, не в `main`: `feature/…`, `fix/…`, `docs/…`,
  `chore/…`.
- Новая ветка создаётся от свежего `main`, PR — в `main`. Длинные цепочки
  PR не заводи: в 22.10.2026 цепочка #15–#22 застряла на merge (GitHub
  не обновил head промежуточного PR). Если задача зависит от
  невлитого PR, проверь `gh pr list --json number,headRefName,baseRefName`
  и ставь базой его ветку, но только на одну ступень.
- Добавляй файлы явно (`git add <пути>`), затем проверь `git diff --cached`.
  Никогда не добавляй `.env`, `.cloudshop-audit/`, `.cloudshop-test-sales/`,
  `target/`, `.claude/settings.local.json`.
- Тема коммита — короткая, на английском, в повелительном наклонении
  (`Add protected staff request view`). В конце сообщения добавь
  атрибуцию, которую требует текущая сессия.

## 4. Push и pull request

`git push` и PR — внешние действия. Выполняй их, если пользователь просил
PR или push либо разрешил это в текущем диалоге. Иначе остановись после
коммита и предложи.

```sh
git push -u origin HEAD
gh pr create --base main --title "<тема>" --body-file <файл>
```

Описание PR пиши на русском, короткими абзацами:
1. что сделано и зачем;
2. на чём основано и с чем сверено;
3. какие проверки выполнены, какие пропущены и почему;
4. что осталось предложением или открытым вопросом;
5. строка «База <ветка> (PR#N), merge не выполняется.»

В конце добавь атрибуцию PR из текущей сессии. Merge не выполняй без
отдельной просьбы; перед merge дождись зелёного CI (`gh pr checks <N> --watch`).

## 5. Запись ссылки на PR

После создания PR допиши в текущий этап `PROJECT_CONTEXT.md`:
«Сохранено коммитом `<sha>` в `<ветка>` от `<база>` (PR#N), отправлено в
[PR#M](<url>), без merge.» Сделай отдельный коммит
`Record <тема> and pull request` и отправь его в ту же ветку.

## 6. Итоговый ответ

Коротко: что изменено (файлы), как проверено (команды и результат), что
не проверено, ссылка на PR, следующий шаг.
