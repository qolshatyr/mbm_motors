## 4. Цель и границы проекта

Создать клиентский сайт для просмотра автозапчастей и отправки заявок на самовывоз. CloudShop остаётся основной системой товарного учёта и обработки продаж.

Требования первой версии:

- Русский язык, цены в тенге, оплата при получении, без регистрации.
- Каталог, категории, поиск, карточка товара, корзина, оформление, подтверждение заявки и контакты.
- Адаптивные страницы для телефона и компьютера без горизонтальной прокрутки основных форм.

- Нет полноценной CRM и управления складом на сайте.

Не входят: замена CloudShop, перенос складского учёта, онлайн-оплата, доставка, VIN-подбор, личный кабинет, бонусы, автоматический резерв, двусторонние бизнес-статусы, массовое заполнение карточек вручную, индивидуальная переработка дизайна после его согласования.

## 6. Каталог и цены

Требования ТЗ:

- Название, артикул, цена в ₸, фото и наличие для выбранного места; в карточке описание и остальные изображения. Для отсутствующего фото — заглушка.
- Поиск по названию и артикулу, фильтры категории/наличия, пагинация.
- Сопоставление по ID CloudShop, не по артикулу. Не объединять разные товары с одинаковым артикулом.
- Нормализацию артикулов согласовать на реальных примерах.
- Публичные категории/метки согласовать с владельцем; не публиковать весь внутренний ассортимент автоматически.
- Удалённые и снятые с публикации товары нельзя добавлять в новые заявки. Исторические позиции сохраняются.
- Цена выбранного места: `store_prices[store_id]`, если задана, иначе `price`. Ноль — заданная цена, а не отсутствующее значение.
- `stock` — количества по ID мест; `in_stock` не гарантирует наличие в конкретном месте.
- Значение скидок, правила единиц и доступность фото ещё требуют проверки.

Предложения, пока не утверждённые:

- Одна заявка относится к одному месту выдачи.
- Не объединять остатки разных мест для выполнения заказа без согласованного процесса перемещений.
- При нулевой цене показывать «Цена уточняется» и блокировать оформление позиции до согласования цены; не продавать бесплатно и не заменять ноль общей ценой молча.

## 7. Корзина, заявки и сохранность

- Корзина в серверной сессии: добавление, удаление, изменение количества. Восстановление после истечения сессии не обещается.
- Форма: имя, телефон, необязательный комментарий. Адрес выдачи показан до отправки.
- Сервер проверяет опубликованность, доступность, единицу и положительное количество; для штучного товара — целое количество. Цены и сумма рассчитываются сервером.
- Изменившуюся цену покупатель подтверждает повторно.
- В одной транзакции сохранить заявку, снимок позиций и задачу интеграции. Повтор с тем же ключом идемпотентности не создаёт новую заявку.
- После надёжного локального сохранения показать номер и текст: «Заявка получена. Магазин подтвердит наличие и время получения».
- Наличие на сайте не является автоматическим резервом.
- Состояния интеграции: `PENDING`, `SENDING`, `SENT`, `FAILED`, `UNKNOWN`. Это технические состояния, не бизнес-этапы заказа.
- `SENT` означает подтверждённое создание документа в CloudShop, а не проведение, оплату или готовность к выдаче.
- После таймаута/неопределённой ошибки — `UNKNOWN`, уведомление сотруднику и сверка; без слепого повтора. Exactly-once между системами не заявляется.
- Уникальный номер заявки передавать в комментарии. Поиск по этому комментарию для восстановления после UNKNOWN ещё не подтверждён.
- Сохранять внешний ID и номер документа.
- Сайт автоматически не проводит продажи и не добавляет оплату.

## 10. Синхронизация

- Первый импорт постраничный; каталог хранится локально.
- Обновления ориентировочно раз в 5 минут после проверки лимитов API.
- Проверить, отражается ли изменение только остатка в `/product/updated`; при необходимости периодическая полная сверка.
- По ранее прочитанной документации обновление источника для `/product` и `/product/{product}` происходит не чаще раза в 3 минуты; мгновенную актуальность не обещать. Точное поведение требует проверки.

- Нельзя удалять весь каталог из-за одного пустого/неполного ответа или неудачного полного обхода.
- Предложение: после 15 минут без успешной синхронизации скрыть точные количества, показать «Наличие уточняется» и принимать заявки с подтверждением менеджером. Порог не утверждён.

### Остатки и журнал

После создания API и интерфейс сохранили Car City=4 и общий остаток=75. История товара за 02–05.10.2026 без фильтров магазина/типа/сотрудника показала только старую продажу №35233, тестовой №35236 в движениях нет.

Удаление/проведение тестовой продажи не выполнялись агентом. Последний известный статус документа — существует, «Новый», непроведённый. Перед новой записью сверять фактическое состояние.

### Поиск и фильтры

- Чтение по `number=35236` без state прошло и вернуло один документ.
- Явный `state[]=1&state[]=2&state[]=3&state[]=4` вернул пустой список, хотя документ имеет state=1. Причина не установлена; не переносить этот фильтр в приложение без проверки.

## 14. Время: установленное поведение теста

Передали строку без смещения `2026-10-03 19:35:33`, сформированную как местное время Алматы. API вернул:

```text
created_at   = 2026-10-03T14:35:43+00:00 → Алматы: 03.10 19:35:43
processed_at = 2026-10-03T19:35:33+00:00 → Алматы: 04.10 00:35:33
```

В этом тесте API интерпретировал строку date как UTC. Разница даты документа с предполагаемым местным временем — 18000 секунд. Время создания отстояло примерно на 10 секунд от начала отправки.

Это объяснило, почему период журнала до 03.10 не показывал документ. После перехода к 04.10 документ найден.

`tools/cloudshop/cloudshop_test_sale.py` исправлен: по умолчанию формирует дату в UTC. **Новая продажа с исправленной датой ещё не создавалась.** Хранить времена в UTC, отображать в Asia/Almaty, различать время создания и время документа. Если API возвращает дату без смещения, нельзя угадывать её зону молча.

## 15. Ошибки, уже устранённые при тестировании

1. Установка через официальный shell installer не смогла записать `/usr/local/bin`. Затем Postman CLI оказался установлен и работал: проверенная версия 1.69.0. Не переустанавливать только по раннему сообщению об ошибке.
2. `collection run --output` в конфигурации пользователя требует Enterprise. Инструкция исправлена без этого параметра.
3. Пустые/потерянные `CLOUDSHOP_ENV` и `CLOUDSHOP_COLLECTION` приводили к отсутствию файла и «expecting a collection to run». Заменено самостоятельными Python-запусками.
4. Явный `postman request --retry 0` отклоняется ошибкой «The value must be a positive integer», хотя справка указывает default 0. Параметр опущен, автоматические повторы по справке выключены по умолчанию.
5. `postman request --body @file` в проверенной CLI фактически отправляет multipart-загрузку файла, несмотря на справку. Проверено реальным CLI на локальном HTTP-сервере. Для тестового POST используется строка JSON, Content-Type/Accept application/json. Токен не помещается в аргументы.
6. Без правильного JSON/Accept получили 302 на главную CloudShop, не создание. После исправления получили явный 422.
7. Фактическая валидация POST /sales требует customer_id и непустой unit. Схема считает покупателя необязательным; исходный пример без покупателя устарел. Не добавлять `type=changes` для обхода проверки: смысл не подтверждён.
8. Скрипт сначала считал успешным только 201 и пометил реальный 200 как UNKNOWN. Исправлено: 200 с валидным внешним id и числовым number означает SENT; запись попытки исправлена, повтор остаётся заблокированным.
9. Уведомление CLI о невозможности публикации локального прогона в cloud не означает ошибку CloudShop. Флаги `--no-report-events` используются; полные результаты с секретами не публиковать.

Все первые неопределённые попытки разблокировались только после ручного подтверждения пользователя об отсутствии документа. История попыток сохранена локально.

## 16. Покупатели: следующий незакрытый выбор

Фактический POST /sales требует существующий customer_id. Нельзя считать вариант «только имя/телефон в комментарии, без customer_id» рабочим.

### Вариант A: отдельные покупатели

По документации POST /customers требует name, описывает type=person/company и phones[]; реальный POST /customers ещё не выполнялся. GET /customers и GET /customers/{customer} проверены по схеме; список реального аккаунта вернул 104 записи. Схема GET показывает billing.phone, но не документирует фильтр телефона и полный список phones[].

Нужны проверка прав, формата телефонов, полноты чтения и надёжной стратегии сопоставления без дублей. Нормализованный телефон не доказывает личность пользователя сайта; не раскрывать и не перезаписывать чужие данные. Параллельные создания нужно ограничить. После неопределённого создания покупателя нельзя слепо создавать ещё одного.

### Вариант B: служебный покупатель

Одна карточка «Покупатели сайта», её ID в серверной конфигурации. Имя/телефон заявки передаются в комментарии после согласования. Отдельных карточек и индивидуальной истории покупателей в CloudShop не будет. Требуется проверить удобство сотрудника и сохранность комментария на тестовых данных.

Оба варианта **предложения, не выбор пользователя**. Не использовать созданного «тестового покупателя» автоматически для production.

## 17. Безопасность и эксплуатация

- Токен только на сервере, вне Git, браузерного кода, логов и общих экспортов. В новый чат токен не передавать.
- HTTPS, БД не открыта публично, хеширование паролей, CSRF, экранирование внешних описаний, серверная валидация и ограничение частоты отправки.
- Не писать полные персональные данные в технические логи. Уведомление об обработке данных и срок хранения согласовать до запуска.
- Резервные копии отдельно от основного сервера; до приёмки проверить восстановление.
- Предложение ТЗ: ежедневный backup, хранение 14 дней. Потеря до суток локальных данных возможна и требует согласования; период/хранение/ответственный фиксируются в инструкции.
- Сбой сайта или интернета может остановить приём заявок, но не означает потерю учёта CloudShop.
- GET-коллекция остаётся только для чтения. Новые тестовые записи — отдельное действие с разрешением владельца, не часть массового прогона.
- Не проводить, не удалять и не повторно создавать документ №35236 автоматически.

| Этап | Оценка из ТЗ |
|---|---:|
| Доступы, реальные данные, тест продажи, неопределённый результат | 8–12 ч |
| Макеты, проект, миграции, окружение | 12–18 ч |

| Корзина и оформление | 14–20 ч |

| Проверки, запуск, инструкция | 20–30 ч |
| Всего | 90–134 ч |

Это исходная оценка, не учёт затраченного времени. Сроки уточняются после проверки интеграции; ожидание материалов отдельно. Изменение с одного места на четыре требует оценки влияния на объём. Если API не обеспечивает необходимое, способ передачи и объём согласуются до основной разработки.

Критерии приёмки:

- Контрольные цены/остатки соответствуют выбранному месту после успешной синхронизации.
- Поиск находит согласованные названия/артикулы, пагинация не теряет товары.
- Оформление с телефона без регистрации.
- Двойная отправка создаёт одну локальную заявку.
- Подмена цены, недопустимые количества и удалённые товары отклоняются сервером.
- Заявка передаётся как непроведённая продажа с верными товарами и контактами.
- Сбои/таймауты имитируются; заявки не исчезают, UNKNOWN автоматически не повторяется.
- Служебные данные защищены, токен отсутствует в публичных файлах/страницах.
- Backup восстановлен в тестовую БД.
- Сотрудник прошёл демонстрацию обработки заявки.

От заказчика ещё нужны/подлежат подтверждению: название и контакты магазина, часы и адреса выдачи, логотип, публичный ассортимент, права на фото, сложные товары, ответственный сотрудник, бюджет инфраструктуры, макеты, процесс приёмки, условия хранения персональных данных. Доступ к API и отдельный тестовый документ уже проверялись, но дополнительные записи требуют отдельного разрешения.
