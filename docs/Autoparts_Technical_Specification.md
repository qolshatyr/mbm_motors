# Техническое задание — сайт автозапчастей с CloudShop
Версия 0.1 • 03.10.2026 • Проект для согласования

## 1. Цель и границы
Создать клиентский сайт для просмотра запчастей и отправки заявок на самовывоз. CloudShop остаётся основной системой товарного учёта. Бюджет согласованной первой версии — 200 000 ₸; домен, сервер, тариф API и дальнейшее обслуживание оплачиваются отдельно.
Базовые допущения: четыре места хранения/продажи компании, русский язык, цены в тенге, оплата при получении, оформление без регистрации. Название магазина, объём каталога, ответственный сотрудник и окончательный срок уточняются до старта.

Уточнение по решению пользователя: каталог должен учитывать все четыре места, показанные в интерфейсе CloudShop. Чтение списка через GET /stores проверено: HTTP 200, два теста успешны.

| Место | ID CloudShop |
|---|---|
| Car City | `64feaaa51c9799143b532fcf` |
| БАКОРДА | `698c479d4bb8342bd30e3c33` |
| жибек жолы АВТО | `64feaa7d401f7a28d35cda23` |
| СКЛАД | `6967a39f62918c7e760f3747` |

API дополнительно возвращает записи «КАССА 1–4» и «Бирлес». Их назначение и соответствие реальным местам не подтверждены; в согласованный список четырёх мест они пока не входят. Проверить, не дублируют ли остатки касс остатки магазинов. Учёт нескольких мест меняет исходное допущение об одном магазине: перед реализацией согласовать правила показа разных цен, выбора места самовывоза и передачи заявки в CloudShop. Термин «выбранный магазин» далее обозначает конкретное место из согласованного списка; модель остатков должна сохранять привязку к каждому месту.

## 2. Пользователи и страницы
Покупатель: каталог, категории, поиск, карточка товара, корзина, оформление, подтверждение приёма заявки, контакты.
Сотрудник: защищённая служебная страница с состоянием синхронизации и передачи заявок. Учёт и обработка продаж выполняются в CloudShop.
Страницы должны быть удобны на телефоне и компьютере, без горизонтального прокручивания основных форм.

## 3. Каталог
Показывать название, артикул, цену в ₸, фотографию, наличие выбранного магазина; в карточке — описание и остальные изображения. При отсутствии фото использовать заглушку.
Поиск по названию и артикулу, фильтры по категории и наличию, постраничная выдача. Правила нормализации артикулов согласовать на примерах магазина, не объединять разные товары по одному артикулу.
Использовать ID CloudShop для сопоставления товаров. Разрешённые к публикации категории/метки согласовать с владельцем: внутренний каталог не обязательно целиком публичный.
Удалённые или снятые с публикации товары недоступны для новых заказов. Исторические позиции заказов сохраняются.
Цену брать для выбранного магазина из store_prices, если она задана, иначе из price. Проверить смысл скидок и единиц цены на реальных товарах. Не считать in_stock достаточным доказательством наличия в выбранном магазине.

## 4. Корзина и оформление
Добавление, удаление, изменение количества. Корзина хранится в серверной сессии; восстановление после истечения сессии не обещается.
Поля: имя, телефон, необязательный комментарий. Адрес самовывоза показан до отправки.
Сервер проверяет доступность позиций, единицы и положительное количество, рассчитывает цены и сумму сам. Для штучных товаров допускаются только целые количества. При изменении цены клиент повторно подтверждает обновлённую корзину.
После надёжного сохранения заявки показывать её номер и сообщение: «Заявка получена. Магазин подтвердит наличие и время получения». Наличие на сайте не является автоматическим резервом.

## 5. Интеграция
Основание: спецификация CloudShop 1.0.14, ранее прочитанная в этой работе: https://connect-api.cloudshop.ru/docs?api-docs.json . Повторная загрузка 03.10.2026 не удалась. Актуальность методов и полей проверяется перед реализацией.
GET /stores — выбор магазина.
GET /product, GET /product/{product} — каталог; GET /product/ext-categories — категории.
GET /product/updated, GET /product/deleted — изменения; точные требования метода удалений сверить перед использованием.
POST /sales с status=false — передача заявки как непроведённого документа продажи. POST /customers — опционально, после проверки схемы, сопоставления и исключения дублей покупателей.
Результат фактического теста 03.10.2026: POST /sales требует customer_id и непустой unit; без них HTTP 422. Существующий тестовый покупатель и unit="шт." позволили создать документ #35236: HTTP 200 с внешним ID и номером (вместо описанного 201), в интерфейсе статус «Новый». Стратегию получения/создания покупателя необходимо согласовать до реализации оформления; считать передачу без customer_id рабочим вариантом нельзя. В интерфейсе дата теста сдвинулась на +5 часов относительно переданной строки; формат и часовой пояс требуют отдельной проверки. Влияние непроведённого документа на остаток и резерв ещё не установлено.
Последующая проверка этого документа: остаток Car City остался 4 шт. в API и интерфейсе, общий остаток — 75 шт. В истории товара за 02–05.10.2026 тестовый документ отсутствует. В данном сценарии списание не наблюдается; влияние на отдельный резерв ещё не установлено. Подробные результаты и ограничения проверки приведены в docs/cloudshop/CloudShop_Postman_Guide.md.
Чтение документа через GET /documents/sales по номеру без фильтра state подтвердило status=false и state=1. Покупатель сопоставляется по customer.id/destination.id; отличающийся client_id нельзя считать ID покупателя без уточнения. Оплаты нет: payment_terms.paid=false, metrics.paid_sum=0, несмотря на financial_status=partially_paid. Возвращаемое количество -1 не является доказательством списания. processed_at содержит переданное время с явным UTC-смещением; приложение должно хранить моменты времени в UTC и отображать в Asia/Almaty. Поиск по номеру проверен, поиск по уникальному комментарию и автоматическая сверка UNKNOWN ещё не проверены.
Первый импорт выполняется постранично. Каталог хранится локально; фоновые обновления ориентировочно раз в 5 минут, после проверки ограничений API. Проверить, отражается ли изменение только остатка в /product/updated; при необходимости применять периодическую полную сверку.
По прочитанной спецификации сверка источника для /product и /product/{product} происходит не чаще раза в 3 минуты. Мгновенная актуальность и гарантированный резерв не обещаются.
Контрольная точка синхронизации продвигается только после успешной обработки; сбой не очищает каталог. Полные проходы и отсутствие товара в одном ответе не должны приводить к случайному массовому удалению.
Предложение для согласования: после 15 минут без успешной синхронизации скрывать точные количества и показывать «Наличие уточняется»; заявки принимать с подтверждением менеджером.

## 6. Сохранность заявок и отправка
В одной транзакции сохранять заявку, снимок позиций и задачу передачи. Повтор формы с тем же ключом не создаёт новую заявку.
Состояния обмена: PENDING, SENDING, SENT, FAILED, UNKNOWN. Это технические состояния, не этапы выполнения заказа.
SENT означает подтверждённое принятие документа CloudShop. Записывать внешний ID, если API его возвращает. Полнота ответа 201 требует теста.
После таймаута или иной неопределённой ошибки не выполнять слепую повторную отправку: документ мог создаться. Помечать UNKNOWN, сообщать ответственному и проводить сверку. До подтверждения механизма API гарантия exactly-once между системами не заявляется.
В комментарий документа добавлять уникальный номер заявки сайта. Возможность поиска по нему и получения внешнего ID проверить отдельно.
Цена и контакты не берутся из доверенных полей браузера без серверной проверки. Сервис не проводит продажи автоматически.

## 7. Служебная страница
Доступ по логину и паролю сотрудника. Показывать номер заявки, время, необходимые контакты, состав, состояние отправки, краткое описание ошибки, время последней синхронизации.
Для UNKNOWN доступна отметка результата ручной сверки; повторная отправка разрешается только после подтверждения, что документ не создан. Сам повтор должен защищаться от параллельного запуска.
Полноценная CRM и управление складом не входят в этот интерфейс.

## 8. Стек и данные
Java 21, стабильная совместимая Spring Boot 4.x, Spring MVC, Thymeleaf, Bootstrap 5, JavaScript, PostgreSQL, Spring Data JPA, Flyway, RestClient, Spring Security, Bean Validation, Maven Wrapper.
Один репозиторий и одно приложение. Модули: catalog, cart, order, cloudshop, sync, admin, security, config.
Таблицы: products, categories, product_images, orders, order_items, integration_jobs, sync_runs, admin_users. Цены BigDecimal/NUMERIC. Контакты покупателя и цена на момент оформления сохраняются в заявке.
Docker Compose для приложения и БД; Nginx для HTTPS. Точные версии и лимиты ресурсов фиксируются при создании проекта.

## 9. Защита и эксплуатация
Ключ API только на сервере, вне Git и клиентского кода. HTTPS; БД не открыта публично; хеширование паролей; защита форм от CSRF; экранирование внешних описаний; серверная валидация и ограничение частоты отправки заявок.
Не писать токены и полные персональные данные в технические логи. Срок хранения заявок и текст уведомления об обработке данных согласовать до запуска.
Резервные копии локальной БД хранить отдельно от основного сервера; перед приёмкой проверить восстановление. Частота, хранение и ответственный за восстановление фиксируются в инструкции. Предварительно: ежедневная копия, хранение 14 дней; это может означать потерю до суток новых локальных данных, допустимость согласуется.
Ограниченная доступность сервера и интернета не означает потерю учёта CloudShop, но может остановить приём заявок на сайте.

## 10. Этапы
1. Доступы, чтение реальных товаров, согласованный тест непроведённой продажи, проверка неопределённого результата — 8–12 ч.
2. Макеты, проект, миграции, окружение — 12–18 ч.
3. Каталог, поиск и синхронизация — 20–30 ч.
4. Корзина и оформление — 14–20 ч.
5. Передача, обработка ошибок и служебная страница — 16–24 ч.
6. Проверки, запуск, инструкция — 20–30 ч.
Оценка 90–134 ч. Календарные сроки уточняются после этапа 1; ожидание материалов учитывается отдельно.

## 11. Критерии приёмки
- Цены и остатки контрольных товаров соответствуют выбранному магазину после успешной синхронизации.
- Поиск находит согласованные реальные артикулы и названия; пагинация не теряет товары.
- На телефоне покупатель оформляет заявку без регистрации.
- При двойной отправке сохраняется одна локальная заявка.
- Сервер отклоняет подмену цены, недопустимое количество и удалённый товар.
- Согласованная тестовая заявка появляется в CloudShop как непроведённая продажа с верными позициями и контактами.
- Сбои и таймауты имитируются в тестах; заявки не исчезают, UNKNOWN не отправляется повторно автоматически.
- Служебные данные защищены; токен отсутствует в странице и публичных файлах.
- Резервная копия восстановлена в тестовую БД.
- Ответственный сотрудник прошёл демонстрацию обработки заказа.

## 12. Условия и исключения
200 000 ₸ за согласованный объём. Предложение оплаты: 60 000 / 80 000 / 60 000 ₸ по старту, рабочей демонстрации и приёмке. 30 дней исправления ошибок согласованных функций после запуска; дальнейшее обслуживание отдельно.
Не входят: замена CloudShop, перенос складского учёта, онлайн-оплата, доставка, VIN-подбор, личный кабинет, бонусы, автоматический резерв, двусторонние бизнес-статусы, массовое ручное заполнение товаров и индивидуальная переработка дизайна после согласования.
Если этап 1 выявляет отсутствие нужных прав или возможностей API, объём и способ передачи заявок согласуются до основной разработки.

## 13. Что нужно от заказчика
Название и контакты магазина; часы и адрес самовывоза; логотип; доступ к API; выбранный магазин; разрешённый публичный ассортимент; данные и права на фото; примеры сложных товаров; ответственный сотрудник; разрешение на отдельный тестовый документ; бюджет инфраструктуры; согласование макетов и процесса приёмки.
