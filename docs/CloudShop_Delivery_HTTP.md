# HTTP-адаптер передачи заявок

Адаптер реализован и проверяется локально. Обычный запуск сайта **не отправляет** покупателей или продажи: `CloudShopDeliveryGateway` и `DeliveryProcessor` создаются явно, не зарегистрированы в Spring. Планировщика и кнопки отправки нет. Новые и старые задачи остаются `WAITING_CONFIGURATION`.

## Контракт

Источник — [официальная OpenAPI CloudShop 1.0.15](https://connect-api.cloudshop.ru/docs?api-docs.json), прочитанная 12.10.2026, и ранее разрешённая проверка ответа продажи. Локальный поднабор — `postman/specs/cloudshop-delivery.openapi.json`.

- Покупатель: `POST /customers`, `type=person`, имя и массив `phones`; подтверждение — HTTP201 и верхнеуровневый строковый `id` из24 шестнадцатеричных символов.
- Продажа: `POST /sales`, `status=false`, выбранный магазин, подтверждённый покупатель, дата UTC, позиции с точными серверными ценами и нулевыми скидками. Платёжных полей нет. Комментарий содержит маркер `MBM-<UUID заявки>` для ручной сверки и комментарий покупателя.
- Подтверждение продажи — HTTP200 (ранее наблюдался) или201 (документирован), корректный `id` и положительный целый `number`. Пустой ответ201 недостаточен. Строковые, дробные и переполненные номера отклоняются.
- Повторных HTTP-вызовов нет. Редиректы запрещены; адрес ограничен официальным HTTPS `/api/v4` либо loopback HTTP с явным портом. Таймаут от1ms до2min, успешный ответ до64KiB. Дублирующиеся JSON-поля и данные после JSON отклоняются. Исключения не сохраняют body, token или cause.

HTTP-адаптер не меняет промежуточные состояния: процессор фиксирует попытку до вызова, сохраняет покупателя до продажи и переводит неопределённый результат в `UNKNOWN`. Маркер комментария помогает человеку найти документ; он **не является внешним ключом идемпотентности**.

## Локальный стенд

Read-only поиск workspace CloudShop `--ownership all` не дал результатов. Mock владельца не найден; этот стенд сгенерирован из указанной официальной схемы и затем ограничен синтетическими запросами. Он не подтверждает права рабочего токена, допустимость телефона или поведение настоящего CloudShop.

`postman/mocks/cloudshop-delivery/` хранит синтетических покупателей и продажи, проверяет исходящие поля и умеет оборвать соединение **после** создания записи. Неописанные вызовы получают501. Служебные `/__test__/reset` и `/__test__/state` существуют только в локальном стенде. Принимается только явный синтетический ключ; рабочий токен не требуется.

В первом терминале (проверено на Postman CLI1.69.0):

```sh
postman simulate run postman/simulations/cloudshop-delivery.sim.yaml --no-history
```

Этот старый CLI запускает member напрямую на4900 и не применяет новый маршрутизатор `postman simulation`. При другой версии используйте проверяемый напрямую mock, сохраняя адрес тестов:

```sh
postman mock run postman/mocks/cloudshop-delivery/config.yaml --port 4900
```

Во втором терминале, из корня проекта:

```sh
postman spec lint postman/specs/cloudshop-delivery.openapi.json --no-report-events
postman collection lint postman/collections/CloudShop-Delivery-Local
postman collection run postman/collections/CloudShop-Delivery-Local --no-report-events

# Только отдельная mbm_test; URL ниже не менять на рабочую БД.
MBM_TEST_DATABASE_URL=jdbc:postgresql://127.0.0.1:5433/mbm_test \
MBM_TEST_DATABASE_USER=mbm MBM_TEST_DATABASE_PASSWORD= \
MBM_DELIVERY_MOCK_URL=http://127.0.0.1:4900/api/v4 \
./mvnw verify -Prelease-site
```

Запускайте коллекцию и Maven последовательно: оба сбрасывают один синтетический mock. Maven создаёт отдельную временную схему в `mbm_test` и удаляет её после проверки. Без переменных тестовый HTTP/DB-сценарий явно пропускается. Адрес стенда ограничен ровно `http://127.0.0.1:4900/api/v4`; коллекция дополнительно запрещает исходящие адреса вне localhost4900. После проверки остановите свой mock через Ctrl+C.

## Результат проверки, 12.10.2026

`./mvnw verify -Prelease-site`: BUILD SUCCESS, 146 Java-тестов, 0 failures/errors, 1 Docker/Testcontainers-вариант пропущен; PostgreSQL-тесты выполнены. Spotless и Python26 прошли. Frontend не менялся; release JAR включает ранее собранный дизайн.

47 HTTP-тестов прошли: payload, точная цена, UTC, ошибки, строгий JSON, размер ответа, редиректы, потеря ответа и таймауты заголовков/тела без повторного POST.

Три сценария реального процессора с PostgreSQL17.6 и HTTP-стендом прошли:

| Сценарий | Фактически создано в mock | Состояние задачи |
| --- | --- | --- |
| Успех и повторный запуск процессора | 1 покупатель, 1 продажа | SENT |
| Ответ покупателя потерян после создания | 1 покупатель, 0 продаж | UNKNOWN, повторов нет |
| Ответ продажи потерян после создания | 1 покупатель, 1 продажа | UNKNOWN, покупатель сохранён, повторов нет |

Количество проверено чтением фактического состояния mock, а не только stub-вызовами. Старый CLI выводит события запуска и текстовые request sent/completed (покупатель201, продажа200); нового NDJSON request-log нет. Независимое ревью существенных замечаний не выявило.
