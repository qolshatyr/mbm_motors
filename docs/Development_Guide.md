# MBM Motors — руководство для разработки

Внутренняя рабочая инструкция по окружению, запуску, синхронизации и проверкам. Все команды выполняются из корня проекта. Обзор для GitHub находится в [README.md](../README.md).

Приватный репозиторий: [qolshatyr/mbm_motors](https://github.com/qolshatyr/mbm_motors). Основная ветка — `main`.

Сайт автозапчастей с CloudShop. Реализованы импорт, синхронизация, каталог с поиском и серверная корзина. Локальное оформление и сохранение снимка заявки реализованы; передача в CloudShop ещё не подключена.

## Окружение

Java 21, Spring Boot 4.0.8, Maven Wrapper 3.9.11, PostgreSQL 17.6. Java 21 совместима с выбранной веткой [Spring Boot](https://docs.spring.io/spring-boot/4.0/system-requirements.html). Для Compose нужен Docker с плагином Compose. Системный Maven не нужен: `./mvnw` загрузит указанную версию.

```sh
java -version
./mvnw verify
```

Spotless проверяет формат Java, JaCoCo формирует отчёт `target/site/jacoco/index.html`; порог покрытия пока не установлен. Форматирование: `./mvnw spotless:apply`.

## Локальная база

Скопируйте `.env.example` в `.env` и задайте локальный `DB_PASSWORD`. Файл исключён из Git. Затем:

```sh
docker compose up -d db
```

PostgreSQL слушает только `127.0.0.1:5432`, данные сохраняются в Docker volume. Альтернатива — собственная PostgreSQL с пустой БД `mbm_motors`; передайте `DB_URL`, `DB_USER`, `DB_PASSWORD` через окружение. Flyway создаёт таблицы при запуске. Hibernate только проверяет схему, не меняет её.

## Первичный импорт

```sh
python3 scripts/run_sync.py full
```

Скрипт скрыто спросит токен CloudShop и пароль БД, если они не заданы в окружении. Укажите пароль, установленный в `.env`; файл не загружается в Java автоматически. Нужен только доступ чтения. Импорт делает GET `/product` до пустой страницы, записывает локальные товары и завершает процесс. На CloudShop ничего не создаёт и не меняет.

## Последующие обновления

```sh
python3 scripts/run_sync.py incremental
```

Если первичного импорта нет или с полной сверки прошли сутки, выполняется полный проход. Иначе GET `/product/updated` начинается за пять минут до контрольной точки предыдущего успешного запуска. Пустая выдача допустима. Все времена хранятся в UTC; для строк API без смещения UTC является явной рабочей гипотезой.

Для фонового процесса с уже настроенными переменными окружения:

```sh
./mvnw spring-boot:run \
  -Dspring-boot.run.arguments="--catalog.sync.enabled=true"
```

Обновления каждые пять минут, полная сверка раз в сутки. По умолчанию расписание выключено; обычный запуск не обращается к CloudShop. Веб-сервер привязан к localhost.

## Просмотр каталога

После первичного импорта запустите:

```sh
python3 scripts/run_catalog.py
```

Откройте http://localhost:8080/catalog. Скрипт спросит пароль БД; токен для просмотра не нужен. Для просмотра с фоновыми GET-обновлениями используйте `python3 scripts/run_catalog.py --sync`: дополнительно потребуется токен чтения. Остановка — Ctrl+C. Эти команды не создают продажи.

Поиск работает по названию, артикулу и коду; `546102t000` также находит `54610-2T000`. По умолчанию выбран Car City. Можно выбрать любую из четырёх точек, включить фильтр положительного остатка и открыть карточку с ценами/наличием во всех точках. Страница содержит 24 товара; фильтры сохраняются при переходе между страницами. Дубликаты артикулов остаются отдельными товарами.

В текущем локальном прототипе нулевая, отрицательная или отсутствующая цена отображается как «Цена уточняется». Единица берётся из API. Через 15 минут после последней успешной синхронизации точное наличие заменяется на «Наличие уточняется» и появляется предупреждение; фильтр при этом использует последний сохранённый остаток. Дата обновления показывается по Алматы. Фото отсутствующих изображений заменяются нейтральной заглушкой. Bootstrap поставляется локально, без CDN.

Это прототип для проверки каталога; правила публикации ассортимента, покупки без цены/единицы и точки самовывоза ещё требуют согласования.

## Корзина

Откройте карточку товара и нажмите «В корзину» у нужной точки. Ссылка на корзину есть в шапке. Одна корзина относится к одной точке хранения; это ещё не согласованный выбор самовывоза. Для смены точки очистите корзину.

Добавление доступно для положительной цены/остатка и единицы «шт» или «шт.» при успешном обновлении каталога не более 15 минут назад. Другие единицы и товары без единицы пока нельзя добавлять. Сервер проверяет условия снова при каждой операции. Максимум — 50 разных позиций и 999 единиц каждой, не больше сохранённого остатка. Цена из браузера не используется для расчёта.

Можно менять количество, удалять позиции и очищать корзину. После изменения цены появляется отдельное подтверждение; если цена снова изменилась после показа страницы, подтверждение отклоняется. Недоступные позиции отмечаются и не включаются в итог доступных товаров. Формы защищены CSRF; корзины разных браузерных сессий независимы. Защита реализована через [Spring Security](https://docs.spring.io/spring-security/reference/7.0/servlet/exploits/csrf.html).

Корзина хранится в памяти серверной сессии: после 30 минут бездействия или перезапуска приложения она может исчезнуть. Корзина не резервирует остатки и не создаёт документы CloudShop. Пока нет кнопки отправки заявки. Выбран способ покупателей: отдельная карточка CloudShop для каждого покупателя; точки выдачи ожидают уточнения у клиента.

## Полный сайт и оформление

Для единого сайта нужны также Node.js ≥22.12 и npm. Сборка:

```sh
python3 scripts/build_site.py
python3 scripts/run_site.py
```

Первый скрипт выполняет `npm ci`, frontend build и `mvnw clean verify -Prelease-site`. JAR содержит React/шрифты/ресурсы и API. Для уже установленных зависимостей допустим `--skip-install`. Launcher проверяет React внутри JAR; пароль PostgreSQL вводится скрыто либо поступает из окружения. Открыть `http://127.0.0.1:8080`, Vite не нужен. `--port` меняет порт, `--sync` отдельно включает GET-only обновление и скрытый ввод CloudShop-токена. По умолчанию синхронизация выключена; свежесть каталога ограничена 15 минутами.

`checkout.pickup-store-ids: []` блокирует отправку для всех мест, пока клиент не утвердил самовывоз. После согласования можно передать launcher `--pickup-store <CloudShop-ID>` для каждой разрешённой точки. Не подставляйте все четыре места хранения автоматически. Для тестовой БД использовался Car City; это не утверждение клиента. Адреса и часы выдачи ещё требуют данных клиента.

Маршруты: `/`, `/products/:id`, `/basket`, `/checkout`, `/checkout/success?key=...`. Legacy `/catalog` и `/cart` сохранены. При обычном `run_catalog.py` root продолжает вести в Thymeleaf; React раздаётся, когда `frontend.enabled=true` и JAR собран с frontend. Не запускайте обычный backend JAR вместо release-сборки с флагом frontend.

V2 создаёт `local_orders` и `local_order_items`. Заявка получает номер только после commit, корзина очищается после успешной записи. CSRF обязателен; ключ идемпотентности привязан к сессии и снимку. Повтор прежнего payload возвращает прежний номер. Восстановление результата доступно в той же сессии, контакты в ответ не включаются. Заявка имеет статус RECEIVED — сохранена локально, не передана/не подтверждена магазином.

Подробные проверки и воспроизведение только на `mbm_test`: [локальное оформление](Local_Checkout_Verification.md). Production-сервер/HTTPS, ограничения публичной отправки, backup/restore и правила хранения контактов ещё не настроены; release JAR не означает опубликованный сайт.

## Что сохраняется

- `products`: внешний ID, название, артикул, код, единица, каталожная цена, category_id, время обновления/импорта.
- `product_offers`: остатки и эффективные цены четырёх согласованных точек, включая СКЛАД.
- `product_images`: полученные ссылки; изображения не скачиваются.
- `sync_state`, `sync_runs`: контрольная точка и история RUNNING/SUCCESS/FAILED.

Артикул не уникален. Пустые карты API `[]` поддерживаются. Нулевая цена точки сохраняется; отсутствие её ключа использует каталожную цену. `null` не превращается в ноль. Отрицательные остатки сохраняются. Единицы не назначаются автоматически, правила продажи товаров без цены/единицы ещё не согласованы. Это хранение данных, а не разрешение публиковать весь ассортимент.

Каталог и контрольная точка фиксируются одной транзакцией после полного чтения. Сбой, повторный ID или предел страниц отменяют импорт без очистки старого каталога. PostgreSQL advisory lock исключает параллельные запуски; пул соединений должен быть не меньше двух (по умолчанию пять). Отсутствие товара при полном обходе не удаляет его: непустая выдача deleted и её семантика ещё не проверены. После аварийного завершения запись RUNNING может остаться в журнале; она не блокирует следующий процесс.

## Проверки

Unit/HTTP-тесты используют локальные ответы, без CloudShop. PostgreSQL integration/smoke test запускается через Testcontainers. При отсутствии Docker он явно пропускается. Для проверки на отдельной локальной тестовой БД (её данные очищаются тестом):

```sh
MBM_TEST_DATABASE_URL=jdbc:postgresql://localhost:5432/mbm_test \
MBM_TEST_DATABASE_USER=mbm MBM_TEST_DATABASE_PASSWORD=local-test-password \
./mvnw verify
```

Используйте только отдельную БД с именем `mbm_test`; не указывайте рабочую БД. Python-проверки API-инструментов: `python3 -m unittest discover -s tests -v`.

Историческая проверка 05.10.2026: `spotless:apply verify` — 41 Java-тест прошёл, один Testcontainers-тест пропущен (Docker socket недоступен); отдельные PostgreSQL-тесты выполнялись на временной PostgreSQL 17.6. Все 20 Python-тестов прошли. Chromium проверил каталог/корзину на копии снимка 8797 товаров, включая гонку изменения цены и CSRF; внешнего CloudShop в этих проверках не было.

Порядок работы с ветками, коммитами и pull requests: [GitHub](GitHub_Workflow.md).

```text
MBM_Motors/
├── README.md                 # Обзор репозитория
├── PROJECT_CONTEXT.md        # Текущее состояние и история решений
├── AGENTS.md                 # Инструкции для работы с проектом
├── pom.xml, mvnw, mvnw.cmd    # Maven и сборка приложения
├── compose.yml, .env.example # Локальная PostgreSQL и шаблон конфигурации
├── src/                      # Приложение, ресурсы, миграции и Java-тесты
├── scripts/                  # Запуск каталога и синхронизации
├── tools/cloudshop/          # Вспомогательные проверки CloudShop
├── tests/                    # Python-тесты инструментов
├── docs/                     # Руководство для разработки, ТЗ и оформление
│   ├── client/               # Вопросы клиенту для Notion
│   └── cloudshop/            # Инструкции и результаты API-проверок
└── postman/
    ├── assets/               # GET-коллекции v2.1 и шаблон окружения
    └── skills/               # Навыки Postman
```

Документация: [список документов](README.md), [ТЗ](Autoparts_Technical_Specification.md), [оформление](Checkout_Flow.md), [вопросы клиенту](client/Client_Questions.md). Текущее состояние и история: [PROJECT_CONTEXT.md](../PROJECT_CONTEXT.md).

Инструменты CloudShop перенесены из корня в [tools/cloudshop](../tools/cloudshop/README.md). Все команды выполняются из корня проекта, например `python3 tools/cloudshop/cloudshop_check_stores.py`. Коллекции и шаблон окружения находятся в `postman/assets/`; пути `.postman/resources.yaml` обновлены. Содержимое коллекций и режим GET-only сохранены.

Локальные `.env`, `.cloudshop-test-sales/` и `.cloudshop-audit/` остаются в корне и исключены из Git. Не удаляйте журнал продаж: он защищает от повторных отправок. `target/` и `__pycache__/` — игнорируемые результаты сборки и Python-кэши.

## Служебный просмотр заявок

После сборки: `python3 scripts/run_site.py --sync --admin --port 8081`. Скрипт приватно запрашивает отдельные логин и пароль сотрудника. Вход — `/admin/requests`; по умолчанию раздел отключён. Подробности и ограничения: [служебный просмотр](Staff_Requests.md).
