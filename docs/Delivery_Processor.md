# Обработчик передачи: внутренний контракт

На этом этапе проверяется механизм передачи, а не HTTP-контракт CloudShop. Рабочий адаптер, scheduler и публичный endpoint отправки отсутствуют. Существующие заявки автоматически не отправляются. Точки выдачи и правила повторных покупателей требуют согласования.

## Этапы

| Состояние | Значение |
| --- | --- |
| WAITING_CONFIGURATION | Заявка сохранена, передача не разрешена |
| READY | Конкретная заявка явно подготовлена внутренним вызовом |
| CUSTOMER_IN_FLIGHT | Попытка создания отдельного покупателя записана до внешнего вызова |
| CUSTOMER_CREATED | Подтверждённый ID покупателя сохранён |
| SALE_IN_FLIGHT | Попытка создания непроведённой продажи записана до внешнего вызова |
| SENT | Подтверждённые ID и номер продажи сохранены |
| UNKNOWN | Результат требует ручной сверки; автоматический повтор запрещён |

Внутренний обработчик принимает UUID конкретной заявки. Конкурирующие вызовы допускают только одну попытку каждого этапа через compare-and-set состояния в PostgreSQL. Между внешними вызовами транзакция не держится. Создание покупателя и создание продажи — разные этапы: подтверждённый покупатель не создаётся повторно после перезапуска.

Любое исключение или неполный ответ переводит выполняемый этап в UNKNOWN. Даже HTTP-ошибка в будущем сама по себе не доказывает отсутствие записи. Перезапуск не повторяет IN_FLIGHT; отдельный внутренний метод переводит зависшую попытку в UNKNOWN после установленной границы времени. Ручное восстановление и повторное разрешение UNKNOWN на этом этапе отсутствуют.

Адаптер получает неизменяемый снимок заявки и позиций, а не актуальные цены каталога. Продажа должна оставаться непроведённой (status=false), иметь дату UTC и не содержать платежей. Номер заявки служит корреляцией, но не является внешним ключом идемпотентности.

В тестовом сценарии покупатель создаётся отдельно для каждой заявки. Повторный запуск той же заявки использует сохранённый ID; переиспользование карточек между разными заявками по телефону не реализовано. Это временная граница механизма, а не согласованное правило для повторных покупателей.

## Границы проверки

Тестовый адаптер возвращает синтетические идентификаторы или имитирует потерю ответа. Он не выполняет HTTP-запросов. Эти проверки не подтверждают формат POST /customers, права токена, телефонную дедупликацию или фактическое создание документа CloudShop.

Postman CLI 1.69.0 не поддерживает `postman simulation`; проверка обновлений skills в sandbox недоступна (EAI_AGAIN). Повторный read-only поиск workspace CloudShop с сетевым доступом (`--ownership all`) не нашёл результатов. Workspace владельца и его mock не установлены. Непроверенный внешний mock не создаётся.

12.10.2026 повторно прочитана [официальная OpenAPI 1.0.15](https://connect-api.cloudshop.ru/docs?api-docs.json): POST /customers требует name, принимает phones[] и описывает ответ HTTP 201 с верхнеуровневым id. Пример телефона без плюса не задаёт допустимый формат всех номеров. Схема не подтверждает права токена и реальный формат ответа. Рабочие контакты и ключи для этого чтения не использовались.

Следующий шаг — проверить HTTP-адаптер на документированном внешнем контракте с локальной simulation, затем согласовать повторных покупателей, старые заявки, точки выдачи и реальную отправку.
