> Все команды выполняются из корня проекта. Коллекции — `postman/assets/`, Python-инструменты — `tools/cloudshop/`. Ранние результаты ниже сохранены как история.

## 1. Импорт
Импортируйте postman/assets/CloudShop_ReadOnly.postman_collection.json и postman/assets/CloudShop_Local.postman_environment.json. Выберите окружение CloudShop — local settings.
В access_token укажите ключ локально. Не публикуйте его и не отправляйте сюда. Не используйте рабочее пространство с ненужными участниками; не экспортируйте заполненное окружение с секретом.
Коллекция передаёт ключ в заголовке X-CloudShop-API-Access-Token. Bearer не нужен.

## 2. Порядок чтения
1. Откройте запрос 01 — Магазины и нажмите Send. Ожидается 200. Сверьте название и адрес; ID именно нужного магазина вставьте в store_id.
2. Запрос 02 показывает категории.
3. Запрос 03 получает первые 10 товаров. Сравните несколько с учётной системой: название options.name, sku, price, store_prices, stock и img. ID одного товара вставьте в product_id.
4. Запрос 04 получает выбранный товар. В ответах по ранее изученной схеме stock — объект с ID магазинов в качестве ключей. Магазины с нулём не включаются. in_stock относится к наличию хотя бы в одном магазине, не обязательно нужном.
5. Запрос 05 проверяет следующую страницу. Позже код должен обходить весь каталог, а не только первые 10 строк.
6. В start_time задайте недавнюю дату, например 2026-10-03 00:00:00. Запрос 06 возвращает изменения с указанного момента. Уточните часовой пояс API; не предполагайте автоматически Asia/Almaty.
Если API возвращает пустой список, проверьте выбранный магазин, права и фактические товары. Это не доказывает неисправность API.

## 3. Как читать ошибки
401 — ключ отсутствует, истёк или не принят.
403 — проверить права конкретного маршрута.
404 — проверить URL и ID магазина/товара.
400/422 — проверить формат параметров и текст ответа.
429 — остановить частые запросы, учитывать Retry-After при наличии.
5xx/таймаут — сбой сервиса/связи. Чтение можно повторить позже. Правила для записи строже — см. ниже.
Во всех случаях сохраняйте код и обезличенное тело ответа; не публикуйте ключи, контакты клиентов и полный экспорт базы.

## 4. Тест передачи заявки — отдельный ручной шаг
Этот шаг ИЗМЕНЯЕТ CloudShop. Выполняется один раз с разрешения владельца, предпочтительно в тестовом аккаунте/магазине. Непроведённый документ нельзя заранее считать не влияющим на резерв: влияние проверить.
Создайте вручную новый запрос POST {{base_url}}/sales с тем же API-заголовком и Content-Type: application/json. Не добавляйте его в массовый запуск коллекции.
В Body выберите raw → JSON. Подставьте проверенные реальные ID, единицу товара, текущую дату и уникальную тестовую метку:

```json
{
  "status": false,
  "store_id": "REPLACE_WITH_STORE_ID",
  "date": "2026-10-03 16:00:00",
  "discount_percent": 0,
  "discount_sum": 0,
  "products": [
    {
      "product_id": "REPLACE_WITH_PRODUCT_ID",
      "quantity": 1,
      "discount_percent": 0,
      "unit": "pcs"
    }
  ],
  "comment": "TEST-SITE-001 — тест интеграции, не выдавать товар"
}
```
Значения даты и pcs приведены как примеры; замените их на согласованные дату/часовой пояс и единицу товара. price не указан: по ранее изученной схеме используется цена каталога. Сверьте фактическую цену документа с ценой нужного магазина. customer_id и payment_details намеренно отсутствуют; сначала проверяем документ без создания покупателя и оплаты.
Ожидаемый результат по документации — HTTP 201. Запишите тело ответа и внешний ID, если он есть. Пустое тело 201 само по себе не означает ошибку: его схема ранее не была подробно описана.
Сотрудник ищет документ по тестовой метке, проверяет позиции, цену, статус, изменение остатка/резерва и затем убирает тестовый документ штатным способом.
При таймауте, разрыве соединения или сомнительном ответе НЕ нажимайте Send повторно автоматически. Сначала проверьте CloudShop: документ мог создаться. Номер в comment помогает ручной сверке, но не гарантирует идемпотентность.

## 5. Что ещё проверить перед разработкой
- Токен ограничен нужными действиями; права чтения и записи проверены отдельно.
- Что возвращается после создания продажи и можно ли надёжно найти её по номеру заявки сайта.
- Можно ли отследить изменения только остатка через /product/updated.
- Фото доступны по ссылкам без авторизации и не истекают неожиданно.
- Поля sku и цены соответствуют реальным данным магазина.
- Как сотрудник получает/находит новый документ и как связывается с покупателем.
- Для первого MVP контакты можно передавать в comment после согласования; создание карточки покупателя проектируется отдельно по актуальной схеме /customers.
- Лимиты API, задержка синхронизации, часовой пояс и семантика резервов.

## 6. Результат проверки
Пришлите только: код ответа каждого выполненного запроса, обезличенный пример одного товара, сведения о полях ответа 201, вывод сотрудника о статусе и влиянии тестового документа. Этого достаточно для уточнения реализации. Ключ API не нужен в переписке.

### Правила для реализации по проверенному сценарию

- Передавать заявку с status=false, непустым unit, customer_id и проверенными ID магазина/товара. Не добавлять payment_details для заявки с оплатой при получении.
- Сохранение на сайте и технический результат передачи отделять от проведения/оплаты в CloudShop. Проверять document_flags.status, а не financial_status или знак количества.
- Сохранять внешние id и number. Подтверждённый в тесте ответ создания — HTTP 200 с обоими полями; схема также описывает HTTP 201. Не считать произвольный HTTP 200 без подтверждения создания успехом.
- Для связи покупателя в прочитанном документе использовать проверенные customer.id/destination.id; смысл client_id отдельно уточнить.
- Работать с моментами времени в UTC, отображать Asia/Almaty. В тесте строка даты без смещения интерпретирована API как UTC. Повторный контрольный POST для новой даты не выполнялся.
- Поиск существующего документа по number без фильтра state проверен. Поиск по comment и поведение state[] отдельно не подтверждены. Не заявлять автоматическую сверку UNKNOWN по метке как готовый механизм.
- Остатки проверенного товара не изменились и движения списания нет; отсутствие отдельного резерва не подтверждено.
- До разработки передачи согласовать создание/сопоставление покупателей без дублей, обработку пустых единиц и нулевых цен, места самовывоза. Лимиты, инкрементальная синхронизация остатков, удаления и фотографии требуют отдельной проверки.
- Особенности Postman CLI 1.69.0: явный `--retry 0` отклоняется; параметр опускается (по справке default 0). `postman request --body @file` фактически передаёт multipart-загрузку; для теста используется строка JSON и заголовки Content-Type/Accept application/json. Без Accept ошибка дала HTTP 302 на главную страницу. Первые неуспешные попытки сохранены локально; отсутствие документа после UNKNOWN проверено пользователем.
