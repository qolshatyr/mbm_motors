# MBM Motors · подготовка товаров CloudShop для сайта

**Дата проверки:12.10.2026.** Это инструкция и проект структуры на согласование. Карточки CloudShop в этой задаче не изменялись; рабочий токен не использовался, продажи не создавались. Источники — официальная справка, публичная OpenAPI1.0.15 и реальные файлы MBM Motors.

> Начинаем с20–30 существующих карточек. Сначала проверяем единицу продажи, затем фотографии и группы. Совместимость с автомобилями ведём отдельно. После проверки небольшой партии переносим правила на остальной ассортимент.

## 1. Что сейчас умеет сайт

| Поле | Текущее поведение |
| --- | --- |
| Название, артикул, код | Импортируются и используются в поиске |
| `unit` | Импортируется; покупка разрешена только для `шт` или `шт.` |
| Цена и остаток по точке | Проверяются сервером; нулевая цена не считается бесплатной |
| `img[]` | Ссылки сохраняются; интерфейс использует первое изображение, разрешены HTTPS-ссылки |
| `category_id` | Сохраняется идентификатор группы; названия/дерево групп и фильтр рабочих категорий ещё не подключены |
| `tags` | Текущий parser не импортирует эти метки |
| `options.description` | Сейчас не импортируется в карточку сайта |
| `packs` | Сайт не поддерживает выбор упаковок и пересчёт количества |
| Автомобиль/поколение/двигатель | Структурированной совместимости пока нет |

**Категории и условные картинки в публичном прототипе — демонстрационные.** Исправление CloudShop не меняет его автоматически: он работает с отдельными тестовыми данными. Рабочий каталог обновляется через GET-синхронизацию.

Основание: `CloudShopProductParser`, `ProductEntity`, `CatalogViewService`, `ProductAvailability`. Для оформления также нужны свежие данные, положительные цена/остаток и согласованная точка выдачи; одна единица измерения не снимает остальные ограничения.

## 2. Группа, категория и автомобиль — разные вещи

CloudShop различает дерево **групп/подгрупп** и несколько **категорий-меток** у товара. В API группа соответствует `category_id`, метки — `tags`. Это подтверждают [справка о группах](https://cloudshop.ru/portal/articles/группы-и-подгруппы-товаров) и [официальная OpenAPI](https://connect-api.cloudshop.ru/docs?api-docs.json).

Для MBM Motors предлагается:

| Что описываем | Где хранить |
| --- | --- |
| Тип детали: амортизатор, бампер, фильтр | Одна основная группа и её подгруппа |
| Дополнительный признак: бренд детали, публикация на сайте | Согласованные метки; сначала проверить их дальнейший импорт |
| Автомобиль, поколение, годы, двигатель, ограничения | Отдельная таблица применяемости, связанная с товаром по CloudShop ID |
| Цена, остатки, основная карточка и фотографии | CloudShop как источник учётных данных |

**Не создаём копию одной детали для каждой машины.** Одна карточка может иметь несколько строк применяемости. Разные физические детали — например левый и правый амортизатор, разные размеры или артикулы — должны оставаться отдельными товарными позициями.

Не используем вариации товара для перечисления совместимых автомобилей: совместимость не означает разные товары. На сайте впоследствии можно получить оба пути: «Ходовая часть → Амортизаторы» и «Марка → Модель → Поколение → Ходовая часть»; они должны вести к одной позиции, а не к дублированным остаткам.

## 3. Подготовка перед редактированием

- [ ] Назначить человека, подтверждающего единицы, комплектацию и применяемость.
- [ ] Выгрузить текущий справочник из «Товары и услуги» через действие скачивания в Excel/CSV. Это исходная копия таблицы, не полная резервная копия CloudShop.
- [ ] Сохранить выгрузку отдельно с датой; проверить, какие идентификаторы она действительно содержит.
- [ ] Для пилотных товаров записать CloudShop ID, артикул, исходную единицу, цену и остаток в каждой точке.
- [ ] Сохранить исходные фото отдельно, если они есть.
- [ ] Согласовать дерево групп и список меток без создания тысяч автомобильных папок.

В официальной справке групповых действий указано, что без ручного выделения действие может относиться ко всему списку. **Перед операцией проверьте фильтр, выделение и количество позиций.** Не запускать изменение цен или удаление при настройке групп. [Групповые операции](https://cloudshop.ru/portal/articles/group-operations).

### Подготовленные таблицы

Файлы находятся в `docs/cloudshop/templates/`:

- `products_to_prepare.csv` — рабочий лист исправления карточек.
- `product_fitment.csv` — подтверждённая применяемость; одна строка на одну связь товар–автомобиль.
- `catalog_groups.csv` — предложенное дерево разделов, статус `proposal`.

Объяснение каждого столбца и проектных статусов — [README таблиц](templates/README.md).

CSV сохранены в UTF-8 с BOM для кириллицы. **Не открывайте заполненный CSV двойным щелчком:** Excel может убрать ведущие нули и округлить длинный числовой код. Импортируйте через «Данные → Из текста/CSV», отключите автоматическое определение типов либо удалите шаг автоматической смены типов в Power Query до загрузки. Для product_id, sku, oem_numbers, engine_code, group_code и parent_code установите текстовый тип. После импорта сверяйте значения с исходной выгрузкой; BOM не защищает числовые идентификаторы. Первые два файла содержат только заголовки: реальных товарных данных туда не добавляли. Это **таблицы подготовки**, а не готовые файлы импорта CloudShop. Их нельзя загружать как обновление справочника без проверки формата и сопоставления полей.

## 4. Исправляем единицы измерения

### 4.1. Определяем, что покупатель получает за количество1

| Реальная схема продажи | Правило |
| --- | --- |
| Одна фара, один фильтр, один диск | `шт`; цена и остаток за одну деталь |
| Запечатанная канистра4л | `шт` допустимо, если1 в учёте уже означает одну канистру; объём указать в названии |
| Физическая коробка/набор как самостоятельный SKU | `шт` допустимо только при учёте одной полной коробки как1 позиции; состав явно описать |
| Масло на разлив по литрам | Сохраняем честную базовую единицу `л`; текущий сайт пока не принимает такую продажу |
| Товар по метрам, килограммам, дробным количествам | Не заменяем на штуки; отдельный этап поддержки сайта |
| Составной/виртуальный комплект CloudShop | Не путать с обычной коробкой; состав и списание компонентов требуют отдельной проверки интеграции |

**Наш стандарт для обычной штучной детали — `шт`.** `шт.` тоже поддерживается, но единый вариант уменьшает путаницу. Непустые `pcs`, `компл`, `упак` и другие значения текущий сайт не принимает. Это ограничение приложения, а не доказательство ошибки учёта CloudShop.

Если единица была пустой, сначала подтвердите, что цена/остаток действительно указаны за штуку. Если учёт был в литрах или отдельных компонентах, замена текста не пересчитывает количества, цены и историю: нужен отдельный согласованный перенос учёта. Не исправляйте такие позиции массовым переименованием.

### 4.2. Меняем одну существующую карточку

1. Открыть CloudShop → «Товары и услуги».
2. Найти товар по артикулу/коду и сверить, что это нужная физическая деталь.
3. Открыть редактирование карточки; название кнопки может отличаться в текущем интерфейсе.
4. Найти блок единиц измерения/упаковки, проверить базовую единицу и настройки упаковки.
5. Для подтверждённой штучной позиции установить `шт`. Не менять закупочную упаковку и её коэффициент произвольно.
6. Сохранить, заново открыть карточку и сверить единицу, цену и остаток.
7. После GET-импорта проверить, что сайт получил правильный `unit`, и добавить товар в корзину. Продажу для этой проверки создавать не нужно.

Блок единиц/упаковки описан в [официальной справке](https://cloudshop.ru/portal/articles/plu-code). Наличие массовой смены единицы в вашем аккаунте или безопасного обновления через Excel **не подтверждено**. Для первой партии используйте ручное редактирование; перед массовым импортом уточните поддержку обновления существующих карточек, сохранение ID и обработку пустых ячеек.

## 5. Фотографии

### Подготовка материала

- Использовать собственную фотографию или файл поставщика/производителя с разрешением на публикацию.
- Сверить артикул, сторону, крепления и комплектацию: похожая деталь не заменяет фотографию нужной.
- Рекомендуемый стандарт MBM: квадратный кадр около1200×1200px, светлый фон, товар целиком и без рекламных надписей. Это рекомендация, не лимит CloudShop.
- Подготовить JPG/PNG; другие форматы применять только после проверки загрузчика.
- Первое фото — общий вид; дополнительные — обратная сторона, маркировка, разъём/крепление.
- Имя локального файла: артикул + ракурс, например `ARTICLE-front.jpg`. Для одного артикула нескольких брендов добавить бренд.

### Загрузка и проверка

1. Найти существующий товар и открыть редактор.
2. Добавить фотографию, сохранить и заново открыть карточку. Возможность загрузки фото в редакторе подтверждена [справкой CloudShop](https://cloudshop.ru/portal/articles/справочники-учет-товаров-и-услуг-мага).
3. Если интерфейс позволяет несколько фото — расставить их и проверить порядок. Поддержка конкретного редактора не проверялась в вашем аккаунте.
4. После GET-синхронизации проверить `img[]` и первое изображение в рабочем сайте. Если есть URL, но изображения нет — проверить HTTPS, доступ без входа, ошибки загрузки и порядок ссылок.
5. Не вставлять путь `C:\...`, ссылку на страницу товара или закрытый облачный файл вместо изображения.

Без фото сайт показывает заглушку. Сейчас все ссылки сохраняются, но покупателю показывается первое фото; полноценную галерею ещё нужно реализовать. Не обещать, что все загруженные ракурсы уже отображаются.

Группа должна отвечать на вопрос «что это за деталь?». Производитель детали, страна и автомобиль не должны заменять тип детали. Например фильтр относится к «Фильтры и обслуживание → Масляные фильтры», а не к отдельной папке каждой машины, которой он подходит.

### Как создать и назначить группы

В веб-версии CloudShop над списком товаров предусмотрено создание группы. Находясь внутри группы, создавайте нужную подгруппу. Для переноса выделите подтверждённые позиции и используйте групповые действия → группы → выбор нужной папки → перенос. Сначала одна карточка, затем небольшая партия. Порядок описан в официальной справке групп.

**Не удаляйте заполненную группу ради перестройки дерева:** по справке удаление группы затрагивает её содержимое. Сначала организуйте перенос и сверку. Единицы, цена, фотографии и артикул при классификации не должны меняться.

После этой подготовки разработчику нужно подключить названия и иерархию групп к сайту. Сейчас сохранённый `category_id` сам по себе не создаёт рабочие разделы.

## 7. Применяемость к автомобилям

Да, покупатель должен иметь возможность выбрать машину и затем раздел деталей. Для точного подбора одной марки и модели недостаточно.

Заполняйте `product_fitment.csv` отдельно от товарного справочника:

| Данные | Что записывать |
| --- | --- |
| `product_id` | ID существующей карточки CloudShop, ключ связи; не придумывать новый ID |
| Марка/модель | Производитель автомобиля и точное название модели |
| Поколение/код кузова | Код и поколение; рестайлинг при значимых отличиях |
| Годы | Подтверждённый диапазон; месяцы/даты выпуска при необходимости — в ограничениях |
| Двигатель/коробка/привод | Код, тип или ограничение, когда это влияет на деталь |
| Сторона/ось | Левая/правая, передняя/задняя, если применимо |
| Рынок/кузов | Регион исполнения и тип кузова, если есть различия |
| `evidence` | Каталог производителя, документ поставщика или другой проверенный источник |
| `confirmed_by`, `state` | Кто подтвердил; `draft`, `confirmed` или `rejected` |

Для каждой машины отдельная строка, один и тот же product_id повторяется. **Не связывайте независимо списки автомобилей и двигателей:** это создаёт ложные комбинации. Пустое поле означает «не установлено», а не «подходит для любого варианта». Если источник доказывает отсутствие ограничения, это надо явно отметить.

Название товара или похожий артикул могут дать кандидатов для проверки, но не подтверждают совместимость. Не относить все детали к машине только потому, что она упомянута в сокращённом названии. «Бренд детали» и «марка автомобиля» — разные поля; OEM-номер, артикул производителя и внутренний код тоже хранить отдельно.

### Где хранить применяемость сейчас

Предложение: CloudShop оставить источником учёта, а проверенную таблицу применяемости затем импортировать в отдельные сущности сайта. Это позволит одной детали подходить нескольким автомобилям без копирования остатков. Пока эту таблицу сайт не читает — это следующий этап разработки.

Для быстрого ручного поиска в CloudShop можно согласовать метки вроде `Авто: ...` и `Бренд: ...`, но это не полноценная база подбора. Не создавайте тысячи меток до проверки пользы и API. Текущий импорт сайта `tags` не читает; нельзя обещать появление фильтров от одного назначения меток.

## 8. Стандарт заполненной карточки

- [ ] Сохранён существующий CloudShop ID; нет дубля ради другой машины.
- [ ] Название понятно, без неподтверждённой совместимости.
- [ ] Артикул записан точно, включая буквы, ведущие нули и дефисы.
- [ ] Бренд производителя детали и OEM-номера подтверждены отдельно.
- [ ] Единица продажи, комплектация, цена и остатки согласованы между собой.
- [ ] Выбрана правильная группа/подгруппа.
- [ ] Есть хотя бы одно корректное фото либо честная отметка «фото нет».
- [ ] Описание содержит состав, сторону, особенности креплений и ограничения при наличии данных.
- [ ] Применяемость подтверждена источником либо оставлена неизвестной.
- [ ] Ответственный одобрил публикацию.

Поля бренда/OEM/публичности в шаблоне — требования к подготовке данных, не обещание их текущего импорта. Метка публикации не фильтрует сайт автоматически: её обработку необходимо отдельно реализовать.

### Названия и артикулы

Рекомендуемый шаблон: тип детали + существенный признак + производитель + артикул. Например, «Амортизатор передний левый [бренд] [артикул]» — это шаблон, а не подтверждённая товарная карточка. Для жидкости добавить объём фасовки. Совместимость в названии указывать только после подтверждения; не заменять артикул длинным списком машин. OEM-номера сохранять отдельно и не считать сам факт похожего номера доказательством применяемости.

## 9. Пилот и проверка после изменений

Выберите20–30 реальных товаров: несколько из каждой востребованной группы, с пустой и заполненной единицей, с/без фото, с известной применяемостью; упаковку и нештучную продажу включите как отдельные случаи проверки, не как автоматически разрешённые позиции.

### Проверка через существующие инструменты

Все команды из корня. Они запрашивают токен скрыто; не вставлять его в команду или чат.

```sh
# Только GET: исходный снимок и аудит.
python3 tools/cloudshop/cloudshop_snapshot_catalog.py
python3 tools/cloudshop/cloudshop_audit_catalog.py

# После ручного исправления пилота — новый снимок/сравнение и импорт в локальную БД.
python3 tools/cloudshop/cloudshop_snapshot_catalog.py
python3 scripts/run_sync.py full
```

Аудит и снимки сохраняются в локальную `.cloudshop-audit/`, не в Git. При сравнении убедитесь, что выбран именно исходный полный снимок; `--compare` позволяет указать его явно. Выгрузка не атомарна: не смешивать сверку с массовыми параллельными правками.

После импорта проверить на **рабочем локальном сайте**, а не в статическом прототипе:

1. Товар найден по артикулу, ID не поменялся.
2. Единица правильная, цена и остаток по точке не исказились.
3. Фото загружается; без фото видна заглушка.
4. Подтверждённая штучная позиция со свежими положительными ценой/остатком добавляется в корзину.
5. Неподдерживаемая единица остаётся честно заблокированной.
6. Количество и сумма соответствуют физической единице продажи.
7. Группа в ответе API соответствует нужной папке; появление дерева на сайте проверяем уже после его реализации.

Проверка добавления/удаления в корзине не создаёт продаж. Существующие тестовые продажи не повторять. CloudShop API-запись для массового обновления товаров здесь не разработана и не запускается.
